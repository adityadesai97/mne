## Architecture

**mne** is a personal finance tracker — a single-page React app backed entirely by Supabase (Postgres + Auth + Edge Functions). No server-side rendering; all logic runs in the browser or in Supabase edge functions.

### Startup & Auth

`src/App.tsx` gates on `config.isConfigured && isSupabaseReady()`. If false, `<Onboarding>` renders. Supabase is initialized at module load time from env vars (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) — there is no `initSupabase()` call. All DB calls go through `getSupabaseClient()`, which throws if the env vars were absent.

`src/store/config.ts` stores the following in localStorage:
- `mne_claude_api_key` — Claude API key
- `mne_groq_api_key` — Groq API key
- `mne_llm_provider` — active LLM provider (`claude` | `groq`; defaults to `claude`)
- `mne_finnhub_api_key` — Finnhub API key for stock quotes
- `mne_coingecko_api_key` — optional CoinGecko Demo key for crypto quotes (crypto works keyless; not part of `isConfigured`)
- `mne_needs_signin` — flag set when the user is signed out
- `mne_theme` — appearance preference (`light` | `dark` | `system`)
- `mne_asset_view` — Portfolio layout preference (`grid` | `list`; unset until the user picks one, in which case Portfolio defaults to `list` on mobile and `grid` on desktop)

`config.isConfigured` is true only when `config.activeApiKey` (key for the chosen provider), `config.finnhubApiKey`, and `!config.needsSignIn` are all satisfied.

On every app load, `src/layouts/AppLayout.tsx` runs a startup effect: loads assets, records a daily net worth snapshot, promotes stale Short Term tax lots to Long Term, and syncs API keys and the LLM provider to `user_settings`.

`src/lib/priceRefresh.ts`'s `refreshPricesOncePerLoad()` refreshes every ticker's price (Finnhub for stocks, CoinGecko for crypto) at most once per page load (module-scoped promise, resets only on a real reload). Home and Portfolio both await it before their initial asset fetch, so whichever page is open on a fresh load renders current prices — not one triggered by AppLayout's own effect, since AppLayout doesn't own the asset state either page renders from.

### Data Model

The current schema baseline lives in `supabase/migrations/20260302000000_baseline.sql`. Key relationships:

`allowed_emails` — email allowlist used when `VITE_RESTRICT_SIGNUPS=true`. Includes an `is_admin boolean` column (the former `admin_users` table was merged in migration `20260331000000`). Admin check uses `public.is_allowed_email_admin()` (SECURITY DEFINER) to avoid self-referential RLS recursion. Managed via the Settings UI.

```
assets ──→ locations      (account lives at a brokerage/bank)
assets ──→ tickers        (stocks only; null for 401k/cash/etc.)
assets ──→ stock_subtypes (Market | ESPP | RSU — one per subtype per asset)
stock_subtypes ──→ transactions  (individual tax lots with cost_price + purchase_date)
stock_subtypes ──→ rsu_grants    (vest_start, vest_end, cliff_date, vesting_frequency, ended_at)
assets ──→ fixed_income_lots     (Bond/T-Bill only — units + cost/unit + purchase_date, like stock tax lots)
tickers ──→ ticker_themes ──→ themes
themes ──→ theme_targets  (optional allocation target %)
```

`assets.asset_type` is free text with a CHECK allowlist (`assets_asset_type_check`, recreated by the bootstrap on every run — so a new asset type must be added to it in a new migration AND `self_host_bootstrap.sql`, or inserts fail with a constraint violation) and the app only creates: `Stock`, `Crypto`, `401k`, `Cash`, `HSA`, and `Fixed Income`. `Fixed Income` is a super type covering CD, Deposit, Bond, and T-Bill accounts — `assets.fixed_income_subtype` ('CD' | 'Deposit' | 'Bond' | 'T-Bill', DB-constrained) records which, alongside `assets.interest_rate` (annual %, Bond coupon) and `assets.maturity_date`, both nullable and only meaningful when `asset_type = 'Fixed Income'`. Migration `20260811000000_add_fixed_income_asset_type.sql` folded the former standalone `CD` and `Deposit` asset types into this super type in place. T-Bills (and any Bond bought below par) sell at a discount and pay face value at maturity rather than accruing periodic interest — `assets.face_value` (nullable, added in `20260811000001_add_face_value_to_assets.sql`) holds the per-unit maturity payout.

**Bond and T-Bill are tradable** (migration `20260811000002_add_fixed_income_lots.sql`): bought in `fixed_income_lots` rows (`count` units × `cost_price` per unit × `purchase_date`), the same "buy over time in lots" shape as a stock's `transactions`, linked directly to `assets.id` (no intermediate subtype table — a Fixed Income asset only ever has one subtype). `assets.price`/`initial_price` are left `null` for these two subtypes; value is derived from lots instead (see Portfolio Math). CD and Deposit remain flat-balance accounts on `assets.price`, same as 401k/Cash/HSA.

**RSU vesting is discrete, not continuous** (migration `20260829000000_add_rsu_vesting_frequency.sql`): `rsu_grants.vesting_frequency` ('monthly' | 'quarterly' | 'annually' | 'continuous', DB-constrained, `NOT NULL DEFAULT 'quarterly'`) records how a grant vests after its cliff — a lump at `cliff_date` (or `vest_start` if no cliff was recorded) covering however many periods elapsed since `grant_date`, then one equal installment every period through `vest_end`, with the cliff absorbing the rounding remainder so installments sum to exactly `total_shares`. `continuous` falls back to the old smooth linear interpolation across `[vest_start, vest_end]`, for a grant nobody's told the app the real cadence of. `rsuVestedSharesAsOf` / `computeRsuVestEvents` in `src/lib/charts.ts` are the one implementation of this math — the RSU vesting progress chart, `computeRsuVestingSchedule` in `src/lib/claude.ts` (the command bar's `get_rsu_vesting_schedule` tool), and `supabase/functions/check-vests` (a self-contained Deno port, since edge functions can't import from `src/`) all key off it. Existing grants were backfilled to `'quarterly'` — the most common real-world schedule — confirmed against an actual user's brokerage statement.

**Crypto is a ticker asset, not a separate model** (migration `20260921000000_add_crypto_asset_type.sql`): a `Crypto` asset uses the exact same `assets → tickers`, `assets → stock_subtypes (always 'Market') → transactions` shape as a Stock — `isTickerAsset()` in `src/lib/portfolio.ts` (true for `Stock` and `Crypto`) is what valuation, P&L, daily change, charts, snapshots, Pulse, and the command bar's position tools key off, never `asset_type === 'Stock'` directly. What differs is only how the ticker is priced: `tickers.kind` (`'stock'` default | `'crypto'`) selects Finnhub vs CoinGecko, and `tickers.coingecko_id` (e.g. `bitcoin`) is the coin id — stored because ticker symbols collide across coins. `src/lib/coingecko.ts` is the one client (batched `/simple/price`, `/search`, 1-year daily `/market_chart`); `ensureCryptoTicker()` (`src/lib/db/cryptoTickers.ts`) resolves a symbol to its coin (best market-cap rank among exact symbol matches), creates the ticker, fetches an initial quote, backfills `ticker_price_history` with a year of daily closes (never overwriting a day we recorded ourselves), and tags it with a fixed `Crypto` theme (Finnhub's sector profile doesn't exist for coins). Prices refresh in `refreshAllPrices()` (one batched CoinGecko call regardless of holdings) and `check-prices` (Deno port). `previous_close` for crypto is derived from CoinGecko's rolling **24h** % change (`derivePreviousClose`), not a calendar-day close — crypto has no market close, so "today's change" for a coin means "vs 24h ago". Crypto exchanges/wallets are `locations` with account type `Crypto` (not `Investment`); `locations_account_type_check` exists only on hosted projects (never in baseline/bootstrap), so migration `20260921000002_allow_crypto_account_type.sql` widens it only where it exists and import/export maps a `crypto` account type through. Precision was widened for crypto (`tickers.current_price`/`previous_close`, `ticker_price_history.price` → `numeric(18,8)`; `transactions.count` → `numeric(20,8)`, `cost_price` → `numeric(18,8)`) — but only for columns that are *bounded and too small*: the hosted project's `tickers.current_price`/`transactions.count`/`cost_price` were already unbounded `numeric` (drifted from the bootstrap's `numeric(12,x)`), and forcing a precision onto those would constrain, not widen, so the migration and bootstrap use a DO block that skips any column with a null `numeric_precision`. **Crypto is excluded from**: `get_company_fundamentals` (stock-only Finnhub data; crypto symbols come back as an error), RSU/ESPP subtypes, and Finnhub-based logo/profile/auto-theme lookups. Portfolio Pulse news for crypto movers comes from Finnhub's general `news?category=crypto` feed filtered by coin name/symbol (`filterNewsForCoin`) — there is no per-coin news source on any free tier, so small coins will often get "no news found". Portfolio Pulse holds crypto to a higher major-move bar than stocks — `CRYPTO_MOVE_BAR_MULTIPLIER` (2×) applied via `moveBar()` at every timeframe, keyed off an optional `crypto` flag carried on `SymbolMove`/`PortfolioExplanationMover` (and on a `PortfolioExplanationThemeMove` only when every member is crypto) — so a coin's routine volatility doesn't crowd the carousel; the portfolio-level bar is unchanged. **No-key UX for existing accounts**: crypto is entirely additive and optional — an account with no crypto holdings makes zero CoinGecko calls and never needs a key, and `isConfigured` doesn't depend on one. An account that adds crypto without a CoinGecko key uses CoinGecko's shared keyless rate limit; when that's exhausted, `CoinGeckoError` (`src/lib/coingecko.ts`) carries a user-facing message pointing at Settings → Update API keys, which flows through the command bar, the Watchlist add form, and (once per page load, from `refreshAllPrices`) a toast so stale crypto prices aren't silent. `check-prices` runs server-side from one shared IP, where the keyless limit is easiest to hit, so it never makes a CoinGecko call per user: users with their own `coingecko_api_key` get their own batched call, and *every other user's coins are de-duplicated into one shared batch* (`supabase/functions/check-prices/coingecko.ts`, chunks of 100 ids, one retry on a 429 honoring a small `Retry-After`, a still-failing chunk is skipped so those coins just keep their last price this hour). Setting the optional **`COINGECKO_API_KEY` edge function secret** (Supabase dashboard → Edge Functions → Secrets) gives that shared batch a Demo key so keyless users' alerts are no longer subject to the keyless limit. A database that hasn't applied the migration surfaces a "needs a one-time database update" error from `ensureCryptoTicker` rather than a raw PostgREST column error; stock-only accounts are unaffected either way (price refresh treats a missing `kind` as `'stock'`).

**`ticker_price_history`** (migration `20260919000000_add_ticker_price_history.sql`) is a daily per-ticker price snapshot table — one row per `(user_id, ticker_id, date)`, upserted in place same as `net_worth_snapshots` (today's row reflects whatever price was live the last time it was refreshed that day, not necessarily the market close). It exists because `tickers` itself only ever stores `current_price`/`previous_close` — no history — and it's the only source of historical per-ticker prices in the app, backing weekly/monthly/yearly/custom-timeframe stock and sector moves in the Portfolio Pulse carousel (see below). Populated from both places prices already get refreshed: `refreshAllPrices()` (`src/lib/db/tickers.ts`, via `recordTickerPriceSnapshots()` in `src/lib/db/tickerPriceHistory.ts`) and `check-prices`' own upsert. There's no backfill for days before this started recording — a newly-added ticker (or a ticker added before this table existed) simply has no history yet, so longer-timeframe cards for it phase in gradually as history accumulates.

Every table has RLS enabled — users see only their own rows.

All DB access goes through thin wrappers in `src/lib/db/`: `assets.ts`, `transactions.ts`, `tickers.ts`, `locations.ts`, `settings.ts`, `grants.ts`, `snapshots.ts`, `themes.ts`, `fixedIncomeLots.ts`. These are plain async functions that call `getSupabaseClient()` directly — no ORM, no query builder abstraction beyond the Supabase JS client.

### Portfolio Math

`src/lib/portfolio.ts` contains all value calculations:
- Stock value = shares (sum of `transactions.count`) × `tickers.current_price`
- Tradable Fixed Income value (Bond/T-Bill) = sum of `fixed_income_lots.count × cost_price` — held at cost, not marked to market (there's no live bond/bill quote feed)
- Other non-stock value (401k, Cash, HSA, CD, Deposit) = `assets.price`
- Cost basis = sum of (`count × cost_price`) per tax lot
- `computeUnrealizedGain` stays stock-only (P&L is a mark-to-market concept; never reported for non-stock assets, tradable or not)
- `computeFixedIncomeExpectedReturn` — a **held-to-maturity projection** for a tradable Bond/T-Bill, distinct from unrealized gain: capital gain/loss to face value at maturity, plus (Bond only) coupon interest accrued from each lot's purchase date to `maturity_date` at `interest_rate`. Returns `null` without lots, `face_value`, or `maturity_date`.
- **"Today's change" is always `computeDailyChange` (current price vs. each stock's `previous_close`, summed over what the user held) — never the net worth snapshot series.** Measured on tax lots via `computeDailyPosition`: a lot bought *before* today is anchored at `previous_close`, but a lot bought *today* (purchase date ≥ the user's local date, `localDateKey()`) is anchored at its own `cost_price`, since those units weren't held for the move up to the moment of purchase; a symbol's percent is its position return (Σ move ÷ Σ start value), aggregated across accounts, and a position bought entirely today is flagged `sinceBuy` (teaser: "moved +X% since you bought it"). A lot with no purchase date or no usable cost keeps the `previous_close` anchor, and when nothing was bought today the result is exactly `shares × (current − previous_close)`. (For crypto, `previous_close` is the price 24h ago and purchase dates are whole days, so "bought today" approximates "bought in the last 24h".) Home's hero figure, the Daily Movers card, and Portfolio Pulse's teaser (`computeMovers` in `portfolioExplanation.ts`) all key off this same stock-only, previous-close-anchored basis, so they can never disagree with each other. `net_worth_snapshots` is a daily historical series for the net worth *chart* only (and it's not swing-anchored the same way — `recordDailySnapshot` overwrites "today"'s row with the live net worth on every app open, so a day-over-day diff off that series reflects whatever net worth happened to be current the last time the app was opened on each of those two days, not either day's actual market close); it was previously (mis)used for the hero's own day-change figure too, which is why that used to disagree with Portfolio Pulse.

**Snapshot backfill** (`backfillHistoricalSnapshots` in `src/lib/db/snapshots.ts`, math in `src/lib/snapshotBackfill.ts`) fills stock/crypto purchase dates that have no real snapshot (days the app wasn't opened) as `nearest earlier real snapshot + (stock/crypto value that day − stock/crypto value on the anchor day)`, each valued at that day's `ticker_price_history` price — so cash/401k/HSA/CD balances are carried at their anchor value instead of dropped (a stocks-only estimate once wrote a false ~50% dip). It never writes before the earliest real snapshot (no anchor) and skips a date if any held ticker has no price within `MAX_PRICE_STALENESS_DAYS`. Backfilled rows aren't marked, so a later gap can anchor on one.

`src/lib/charts.ts` derives chart datasets (allocation, P&L, capital gains exposure, RSU vesting progress) by transforming the deeply-nested asset graph returned by `getAllAssets()`.

### LLM Abstraction Layer

`src/lib/llm.ts` provides a unified LLM client interface supporting multiple providers:

- **Claude** (`claude` provider) — uses `@anthropic-ai/sdk` via a `ClaudeAdapter` that converts OpenAI-format messages/tools to the Anthropic API shape and normalizes responses back to OpenAI format.
- **Groq** (`groq` provider) — uses the `openai` npm package pointed at `https://api.groq.com/openai/v1`.

`createLLMClient(provider, apiKey)` returns an `LLMClient` that implements the OpenAI `chat.completions.create` interface regardless of the underlying provider.

Models used: `claude-sonnet-5` (Claude), `llama-3.3-70b-versatile` (Groq). Both are defined in `MODEL_FOR_PROVIDER`.

All AI features (`src/lib/claude.ts`, `src/lib/autoThemes.ts`) call `createLLMClient(config.llmProvider, config.activeApiKey)` so they work with either provider.

### AI Command Bar

`src/lib/claude.ts` is the core AI feature. The command bar (⌘K / Cmd+K) collects natural language input and routes it through the LLM. File attachments (CSV, PDF, image) are parsed by `src/lib/fileParser.ts` and injected into the prompt. The agent runs a read-tool loop until a write or navigation tool is selected.

**Read tools** (loop freely, no confirmation):
- `get_portfolio_summary` — high-level net worth + allocation stats
- `get_positions` — detailed position rows
- `get_transactions` — tax lot details
- `get_net_worth_timeseries` — historical net worth snapshots
- `get_exposure_breakdown` — breakdown by ticker / theme / asset_type / location
- `analyze_tax_lots` — short/long-term capital gains analysis
- `simulate_portfolio_actions` — hypothetical what-if scenarios
- `recommend_actions_for_goal` — goal-based recommendations
- `get_rsu_vesting_schedule` — shares vesting between two dates, per grant (discrete installment math, not a smooth-curve estimate)
- `get_company_fundamentals` — valuation/profitability metrics, most-recent-fiscal-year capex, and latest analyst recommendation trend for up to 5 symbols, via Finnhub's free-tier `stock/metric`, `stock/financials-reported`, and `stock/recommendation` endpoints (same `finnhub_api_key` used elsewhere, no new provider; `stock/financials` with `statement=cf` is NOT free and is deliberately not used). Capex has no dedicated Finnhub field — `findCapexLineItem()` in `src/lib/claude.ts` pattern-matches the SEC "as reported" cash flow statement's XBRL `concept` field against known capex concepts (`us-gaap_PaymentsToAcquirePropertyPlantAndEquipment` and siblings, confirmed against a live AAPL 10-K filing), falling back to a label-text match; returns `null` when no line item matches, not an error. Returns raw data only — the tool description explicitly tells the model never to state its own buy/sell/hold call from it, matching `recommend_actions_for_goal`'s existing "educational guidance only" framing rather than opening a stock-picking-advice surface.

**Navigation tool** (no confirmation):
- `navigate_to` — routes to a page

**Write tools** (require user confirmation before executing):
- `add_stock_transaction` / `add_stock_transactions` — stocks only (shares, subtype Market/ESPP/RSU)
- `add_crypto_transaction` / `add_crypto_transactions` — crypto has its own command bar surface rather than a flag on the stock tools: fields `symbol`, `units` (fractional, up to 8 decimals), `cost_per_unit`, `purchase_date`, `location_name` (exchange/wallet), optional `ownership`/`asset_name`; no subtype, no `account_type` (the location is always account type `Crypto`), and the confirmation preview says "Crypto Purchases" with Coin / Units / Cost/Unit / Exchange / Wallet columns and keeps price precision ($164.882, not $164.88). `cryptoToStockTransactionInput()` maps it onto the shared ticker-lot storage path in `executeTool` (the storage model is deliberately shared — see Data Model). `location_name` must be stated by the user: the prompt forbids assuming one, and `findCryptoPurchasesWithUnstatedLocation()` is a deterministic guard in `runCommand` — if the model calls a crypto write tool with an exchange that doesn't appear anywhere in the user's messages, the app replies with a question instead of showing a confirmation (skipped when a file is attached, where a document can identify it). This is the silent-assumption backstop to the general ask-and-write guard above.
- `add_cash_asset` / `add_cash_assets` — for Bond/T-Bill, takes `count`/`cost_price`/`purchase_date` (the first lot) instead of `price`
- `add_fixed_income_lot` / `add_fixed_income_lots` — buy more units of an *existing* Bond/T-Bill position
- `add_ticker_to_watchlist`
- `add_ticker_themes`
- `add_rsu_grant` / `add_rsu_grants` — optional `vesting_frequency` (monthly/quarterly/annually/continuous), defaults to quarterly
- `sell_shares` — stocks (shares)
- `sell_crypto` — crypto sales on the same crypto-native surface as `add_crypto_transaction(s)`: `symbol`, `price_per_unit`, `sale_date`, `location_name` (exchange/wallet), plus `units` + `purchase_date` for one lot or `lots[]` of `{purchase_date, units}`, and the same optional proceeds-transfer fields. `cryptoSaleToSellSharesInput()` maps it onto the shared `sell_shares` logic in `executeTool` (units → count, price_per_unit → sale_price, location_name → source_location_name), so lots, fully-sold-asset cleanup and proceeds transfers behave identically; the confirmation says units / per-unit price / exchange instead of shares, and the sell error messages use "units" for a crypto ticker. The unstated-exchange guard covers `sell_crypto` too.
- `update_asset_value` — rejects Bond/T-Bill assets; their value is derived from lots, use `add_fixed_income_lot` instead

**A write is held whenever the model asks a question in the same response** (`asksUserAQuestion()` in `runCommand`, applies to every write tool): the confirmation is built from the tool call alone and would otherwise discard the question, so a model that asked for missing information while *also* calling the tool had its guess win. When the accompanying text ends a sentence with `?` (ignoring code spans and URLs), the app shows that text as a normal reply and makes no confirmation — the user's answer arrives as the next message and the model retries. The system prompt also tells the model never to ask and call a write tool in one response; the guard is the deterministic backstop. Crypto adds a second, narrower guard for the silent case (a value assumed with no question asked): see `add_stock_transaction` below.

Write operations display a structured preview table in the UI before the user confirms. Multiple write tools in one agent turn are batched into a single confirmation dialog. Prefix commands with `mock:` to test the UI flow without making API or DB calls.

The command bar requires the user to be signed in; if not, it prompts re-authentication.

**File attachment support**: The command bar accepts CSV (text-injected), PDF (pdfjs-dist text extraction + base64 for Claude), and image files. Images require the Claude provider — switching to Groq while an image is attached will throw.

### Portfolio Performance Explanation

An LLM-generated summary of why the user's portfolio moved, generated entirely on demand — there is no scheduled/background generation at all, so (unlike the other AI features) there's no settings toggle for it; there's nothing to opt out of costing anything until it's actually clicked. **Shown on Home** (`Home.tsx` renders `<PortfolioPulseCarousel assets={assets} netWorth={totalValue} />`). Home surfaces **Portfolio Pulse** (`PortfolioPulseCarousel.tsx`), an auto-scrolling carousel of one-line, zero-cost teasers — each card names a *currently relevant* insight (a stock's move, a sector's move, or the whole portfolio's move, at whatever timeframe actually stands out: daily/weekly/monthly/yearly, or a "notable move" over some other window) and clicking it opens a command bar session that fetches or generates that one card's actual explanation. `portfolio_explanations` is keyed by `(user_id, scope, scope_key, timeframe)` — one row per independent insight (`scope`: `'stock' | 'sector' | 'portfolio'`; `scope_key`: the symbol/theme name, or `''` for portfolio scope; `timeframe`: `'daily' | 'weekly' | 'monthly' | 'yearly' | 'custom'`, with `window_days` as the actual day-count behind it) — upserted in place per slot, no history table; `llm_usage_log` is where per-generation trends live.

- **`PortfolioInsightSlot`** (`{ scope, scopeKey, timeframe, windowDays }`) identifies one carousel card/insight; `DAILY_PORTFOLIO_SLOT` is the one that existed before the carousel. `computeMovers`/`buildTeaser`/the default `shouldRegenerate` behavior are untouched and remain the exact basis for that one slot. `computeMoversForWindow(assets, netWorth, priceHistory, windowDays, timeframe)` is the weekly/monthly/yearly/custom counterpart — same attribution pipeline (via a shared internal `attributeMoves`), sourced from `ticker_price_history` (see Data Model) instead of `previous_close`, with move-size bars scaled per timeframe (`MAJOR_MOVE_STOCK_PCT_BY_TIMEFRAME`/`MAJOR_MOVE_PORTFOLIO_PCT_BY_TIMEFRAME` — a 5% daily stock move is notable, a 5% yearly move isn't). A stock with no `ticker_price_history` row old enough for the requested window is simply excluded from it, which is what makes longer-timeframe cards phase in gradually as history accumulates. **Window moves measure what the user held, not the asset**: each tax lot contributes `units × (currentPrice − anchor)`, where the anchor is the ticker's price at window start for a lot bought before the window but the lot's own `cost_price` for a lot bought *inside* it (those units weren't in the portfolio for the earlier part of the window — a coin up 158% this week is a flat week for a position opened at today's price); a symbol's percent is its position return over the window (Σ gain ÷ Σ start value), aggregated across accounts. A position whose lots were *all* bought inside the window needs no price history and is flagged `sinceBuy` (teaser says "moved +X% since you bought it"; the LLM prompt notes it's a return since purchase); a lot with no `purchase_date` counts as held the whole window. The daily path measures what was held too: see Portfolio Math (`computeDailyPosition`).
- **`computeCandidateSlots(assets, netWorth, priceHistory)`** is what the carousel actually renders — every slot currently crossing its own bar, across daily/weekly/monthly/yearly for all three scopes, plus a "notable move" catch-all: `CUSTOM_WINDOW_DAYS` (14/45/60/90/120/180/270) are scanned for a stock/sector move that stands out over some non-calendar window (e.g. a story that took 60 days to play out) without already being covered by a fixed-timeframe slot for that same symbol/theme — at most the two most extreme finds are kept. Deduped to one slot per subject (`scope:scopeKey`, shortest timeframe wins) so the same stock/sector/portfolio never shows as several near-identical cards. Returns `[]` when nothing's relevant, in which case the carousel renders nothing.
- **The carousel is ranked, capped, and de-noised** (`computeCandidateCards` returns `{ slot, score, tag? }`; `computeCandidateSlots` is just its slots). `score` is how much the card moves net worth, in percent of net worth (portfolio: `|dayChangePercent|`; stock: `|dollarChange|/netWorth`; sector: net member dollars/netWorth) — the same scale event cards use, so both kinds rank together. Filters in `deriveCardsFromResult`: (1) **dollar floor** — a stock/sector card must move net worth by ≥ `MIN_CARD_NET_WORTH_PCT` (0.25%), however big its percent; (2) **since-you-bought is held to a higher bar** — `SINCE_BUY_BAR_MULTIPLIER` (1.5×) on the timeframe bar, plus the position must be ≥ `SINCE_BUY_MIN_HOLD_DAYS` (3) old, and on the **daily** path a position whose oldest lot was bought today gets no card (`heldDays`, carried on `SymbolMove`/`PortfolioExplanationMover`, is days since the *oldest* open lot; undefined if any lot lacks a `purchase_date`); (3) **stocks fold into their flagged sector's card** at the same timeframe unless that stock alone is ≥ `DOMINANT_MOVER_CONTRIBUTION_PCT` of the sector's gross swing (folded keys are excluded from the custom-window scan so they can't resurface); (4) the **custom "notable move" catch-all keeps one card**, not two; (5) the final list is capped at `MAX_PULSE_CARDS` (5). Portfolio teasers also say when one holding accounts for ≥ `CONCENTRATED_SWING_PCT` (60%, but <99.5% so a one-holding portfolio doesn't trigger it) of the swing. **"Why now" tags** (`whyNowTag`, from the `ticker_price_history` already loaded): "New N-month/52-week high/low" when the price is the extreme of ≥90 days of history, or "Reversal after a X% run up"/"Rebound after a X% slide" when a weekly+ window moved against the prior equal-length window by ≥ `REVERSAL_PRIOR_MOVE_PCT` (10%). `isSlotSeenAndUnchanged()` (a stored explanation exists, comparable, and `shouldRegenerate` says nothing material changed) marks a card as already-handled.
- **Event cards** (`src/lib/portfolioPulseEvents.ts`) are the non-price insights sharing the carousel — pure JS over data already in memory, no LLM call, educational wording only. Kinds: `rsu_vest` (a discrete vest event within 14 days, via `computeRsuVestEvents`), `long_term` (a Short Term lot reaching its one-year mark within 30 days with ≥$500 unrealized gain — the same date `promoteStaleShortTermLots` flips it), `harvest` (a position ≥15% and ≥$500 under cost basis — it can't tell whether the account is taxable, so wording is "possible candidate"), `allocation_drift` (a theme with a `theme_targets` row ≥5 points off target, share computed like the theme distribution chart), `earnings` (Finnhub `calendar/earnings` within 7 days for only the 5 largest *stock* holdings, one call each, cached per symbol per page load, best-effort). Each carries a `score` (net-worth percent at stake; earnings is position weight × `EARNINGS_TYPICAL_MOVE`, 5%) and a `question`. **Clicking an event card opens the command bar with that question typed in but not sent** (`openCommandBarWithPrompt` in `commandBarBridge.ts` → `AppLayout` → `CommandBar`'s `prefillQuery`). The carousel merges both kinds through `rankPulseItems`: cards the user hasn't dealt with come first (by score), already-opened-and-unchanged price moves and already-opened events (`mne_pulse_seen_events` in localStorage, keyed per occurrence — the id includes the date) are demoted behind them, then the list is capped at 5. The carousel fetches `getAllThemes()` (for targets) and `fetchUpcomingEarnings()` itself; either failing just means those cards don't appear.
- **`buildSlotTeaser(slot, result, previous)`** is the scope-aware counterpart to `buildTeaser` (`buildSlotTeaser(DAILY_PORTFOLIO_SLOT, ...)` reproduces `buildTeaser`'s output exactly) — narrows `result` to just that slot's own story via `scopeMoversResult` (a 'stock' slot's view is just that one mover; a 'sector' slot's is just that one theme + its member movers; 'portfolio' is unchanged) before wording the one-liner.
- **`generatePortfolioExplanation(slot, options)`** takes a `PortfolioInsightSlot` — same orchestration shape as before (load assets → compute the slot's own move → check the stored row for that exact slot → cache hit or fetch headlines + call the LLM → upsert), narrowed via the same `scopeMoversResult`. `shouldRegenerate(current, last, resetsDaily = true, stockPct = MAJOR_MOVE_STOCK_PCT)` gained both params — only `timeframe === 'daily'` resets on a new market day regardless of swing size (rolling weekly/monthly/yearly/custom windows have no such discrete boundary and rely purely on the hysteresis/membership checks below), and `stockPct` is the timeframe-scaled bar used to decide which movers/themes count as "significant" for the membership-change check (so a weekly slot doesn't get flagged stale by a change too small to matter at that timeframe).

`src/lib/portfolioExplanation.ts` is the one implementation of the attribution math and generation orchestration — no edge function, no Deno port, since nothing runs unattended anymore.

- **Each carousel card costs no LLM call** — `PortfolioPulseCarousel.tsx` computes `computeCandidateSlots` from already-loaded `assets`/net worth plus one batched `ticker_price_history` fetch (covering ~372 days, enough for every timeframe/window it checks), then `buildSlotTeaser` per slot (pure JS) plus one cheap `portfolio_explanations` read per slot (just to tell "you already saw this" from "something new happened," see below). Cards sit in a native horizontally-scrolling, scroll-snapped strip — auto-advancing on a timer (paused on hover, and temporarily after a manual swipe/scroll) but also directly swipeable/scrollable by hand, with uniform dot indicators (not width-varying, to avoid reading as an on/off toggle) to jump straight to one; renders nothing when `computeCandidateSlots` returns `[]`. Sized `md:col-span-6` (full grid width) as its own dedicated row directly below the Net Worth hero — everything after it (Allocation, P&L, …) simply flows one row later than it would without this card, with no other change to their widths, order, or arrangement. Earlier attempts tried to match the hero's `col-span-4` width instead, but that always means sharing a row with a `col-span-2` neighbor (Allocation) — and since that neighbor is taller, either the card stretches to match it (default CSS Grid `align-self: stretch`) or, with `self-start`, empty background shows below the shorter card. Full width is the only option with zero dead space anywhere.
- **`shouldRegenerate()` checks three independent levels — portfolio, sector, and individual stock — any one is enough on its own to trigger a fresh explanation**, not just the aggregate swing: (a) the slot's own swing has moved meaningfully past what's stored, or flipped sign (`REGENERATION_HYSTERESIS_PCT`); (b) the *set* of individually-significant movers differs from what's stored — a new holding joining the story, even with a similar-looking aggregate swing; (c) the *set* of flagged theme/sector moves differs from what's stored — same idea, sector-scoped; (d) for `'daily'` only, the stored explanation is from an earlier market day — `portfolio_explanations.market_date` (compared against `todayMarketDate()`, a plain UTC calendar-day key, same granularity as `net_worth_snapshots.date`/`tickers.last_updated` elsewhere in this app) resets it at the next market open regardless of how small the swing looks so far.
- **A slot's teaser calls out specifically what's new, not a repeat of what you already read.** When a slot's stored explanation is comparable (same market day for `'daily'`; any prior row for a rolling window) but now stale per `shouldRegenerate()`, `buildSlotTeaser()`/`buildTeaser()` names the newly-flagged sector ("New activity in Semiconductors since your last check...") or newly-significant mover ("NVDA just moved...") rather than the generic first-time framing — falling back to a plain "changed since your last check" line only when it's a portfolio-level-only change with no new sector/stock to name. **Sector is a first-class framing on the first check too, not just in the "what's new" path above** — the generic branch picks, in order: one dominant holding ("CRM moved +4.10% today..."), otherwise a portfolio-led line naming the flagged sector as context ("Your portfolio went up 1.20% today, with Semiconductors moving the most..." — deliberately not a "Your X holdings moved..." opener, since this card opens the portfolio-wide question and sector moves get their own card; picking the theme with the largest average move when more than one is flagged), otherwise several individually-significant movers ("5 items in your portfolio moved substantially..."), otherwise the aggregate swing alone ("Your portfolio went up 1.20% today..."). Both branches agree that a named sector outranks a plain mover count.
- **A regenerated explanation carries the still-relevant parts of the earlier one (for that same slot) forward, rather than replacing it outright** — e.g. a noon explanation about one stock, then a semiconductor-sector move at 3pm, produces an explanation covering both, not just the sector move alone. `generatePortfolioExplanation()` passes the prior comparable summary (via `stripSources()` — its own "Sources" list is irrelevant/rebuilt fresh) to the LLM as context, and `explanationSystemPrompt()` instructs it to fold still-current content in rather than dropping it or just concatenating the two. For `'daily'` only within the same market day — a prior day's story is dropped entirely, not folded into today's.
- **The actual explanation is generated only when a user asks for it** — clicking a carousel card (`openPortfolioExplanationInCommandBar(slot)` in `commandBarBridge.ts`) opens the command bar, which shows that slot's seeded question (`explanationTriggerQuestion(slot)` — e.g. "Why did NVDA move this week?"; `DAILY_PORTFOLIO_SLOT`'s is still the exact legacy "Why is my portfolio moving?") immediately and calls `generatePortfolioExplanation(slot)` itself (see `CommandBar.tsx`'s `startExplanationRequest` handling, now a `PortfolioInsightSlot | null` prop rather than a boolean), using its normal loading/thinking UI while that runs.
- A quiet day (no major move) short-circuits to a static, deterministically-built string — zero LLM tokens, zero news calls.
- News grounding is fetched by the app's own code (Finnhub, using the existing `finnhub_api_key` — no new provider), never left to the LLM's own knowledge, and only for what's actually moving: `/company-news` for the (≤5) actual movers, `/news?category=general` only when a majority of holdings moved together (`isBroadMarketMove`). Only `headline`/`source`/`url`/`datetime` are kept from Finnhub's response.
- "Sector" moves reuse the app's existing `themes`/`ticker_themes` construct (there's no formal sector column) — grouping data already in memory, no extra fetch.
- The model returns plain prose — it's shown as a normal command bar reply, not a specially-rendered card; the richer structured data (`movers`/`theme_moves`/`market_headlines`) stays in the DB row for trend/debugging purposes even though the chat bubble doesn't render it specially.
- **Links are interactive highlights, never written into the prose by the LLM.** The model is only ever shown a headline's title/source (never its URL — see `buildExplanationUserPrompt`), so it has no URL to get wrong or invent, and its reply is plain prose with no links or markup at all. `ExplanationMessageContent` (`src/components/ExplanationMessageContent.tsx`) renders that prose with mover/theme names highlighted as clickable spans — matched by substring against the row's stored `movers`/`theme_moves`, not parsed out of the model's text — and clicking one shows that mover's/theme's numbers plus its headline links right below, the same interaction the original (pre-command-bar) explanation card had. Broad-market headlines (`market_headlines`, not tied to one mover) show as their own small always-visible list. `CommandBar.tsx`'s `MessageBubble` renders this instead of the normal markdown path only for the one assistant message that carries `explanationDetail` (`ConversationMessageExplanationDetail`, stored alongside that message in `command_conversations.messages` so it still works after resuming a saved conversation); everything else, including follow-up replies in the same conversation, renders as a normal command bar message. `stripSources()` is a defensive strip for a summary generated by an older version of this feature, which did append a flat links list to `summary` directly — no longer done.
- Claude calls pass `output_config: { effort: 'low' }` (Sonnet 5 runs adaptive thinking by default otherwise) and `max_tokens: 600` — the `finish_reason` is normalized on `NormalizedResponse` so a reply that still hits the cap is trimmed to its last full sentence (`trimToLastSentence`) instead of ending mid-thought.

`portfolio_explanations.trigger` is always `'manual'` now (every generation is user-triggered); `'major_move'`/`'market_close'` are historic values from when this used to run on a schedule, kept in the type only because old rows may still carry them.

### Token Usage Tracking

`llm_usage_log` is an append-only ledger shared by both LLM-powered features (portfolio explanations and the command bar) — the one place either's usage can be trended over time. Both `src/lib/llm.ts` adapters (`ClaudeAdapter`, `GroqAdapter`) normalize `usage: { inputTokens, outputTokens }` onto every response; Groq's OpenAI-compatible stream needs `stream_options: { include_usage: true }` or it never emits usage at all.

Each feature also denormalizes its own display copy so showing usage never requires querying/aggregating the log: `portfolio_explanations.input_tokens`/`output_tokens` (this generation's totals) and `command_conversations.total_input_tokens`/`total_output_tokens` (summed across a conversation's turns via `incrementConversationUsage`). `runCommand`'s `AgentTrace` carries a turn's accumulated `usage` (summed across every internal tool-use round through the same `runLLM` closure) so the command bar can display it without new plumbing.

Usage numbers stay hidden until asked for: `TokenUsageInfo` (`src/components/TokenUsageInfo.tsx`) renders a small (i) icon that reveals them in a click-triggered tooltip (not hover, so it works on touch), used on each command bar reply — including a portfolio explanation, which lands there as a normal reply once generated. Feedback submitted on a reply (`FeedbackForm` in `CommandBar.tsx`) carries that turn's usage and the conversation's `origin` into `command_feedback.input_tokens`/`output_tokens`/`conversation_origin` — see below.

`command_conversations.origin` (`'command_bar' | 'portfolio_explanation'`) records which surface started the conversation — set once at creation, read back on resume so `FeedbackForm` can pass it through. `saveConversation({ origin })` only honors this on the initial insert; `CommandBar.tsx`'s handling of a portfolio-explanation open request is what sets it to `'portfolio_explanation'` before persisting that first exchange, so it's evident on review when feedback came from a session that began there rather than a typed command.

### Import/Export

- `'all'` ("All data") — the same bundle plus two more sheets: `NetWorthSnapshots` (from `net_worth_snapshots`) and `Conversations` (AI command bar history from `command_conversations`, flattened one row per message since a spreadsheet has no nesting).

Internally, `serializeForExport()` builds a schema-versioned canonical JS object (`mne.export.v2`) exactly as before; `buildExportWorkbook()` is the only new layer, turning each `data.*` array (plus `snapshots`/`conversations` for `'all'`) into a sheet with explicit, stable camelCase headers. An imported asset row matching that key is upserted onto the existing asset's id — re-importing the same backup (or one that dropped ids) updates positions in place instead of creating duplicates. Net worth snapshots dedup via the DB's `(user_id, date)` unique constraint; conversations dedup by id when the import row carries one (always true for `mne`'s own exports).

### Plaid Integration

Each signed-in user brings their own free Plaid developer credentials (`client_id`/`secret`, entered in Settings or the optional Onboarding `'plaid'` step) — not one credential set shared across the deployment. This means the free Trial plan's 10-connected-account cap belongs to each user individually, and there are no deployment-level Plaid secrets to configure.

Data model (`supabase/migrations/20260908000000_add_plaid_integration.sql`):
- `plaid_credentials` — per-user `client_id`/`plaid_env`, owner-readable, plus a `secret_set` boolean (see Gotchas — this is the only way the client can know the secret below actually saved).
- `plaid_credential_secrets` — the `secret`, RLS enabled with **no select policy at all** (write-only from the client's perspective, like a password field — only a service-role edge function ever reads it).
- `plaid_items` — one row per connected institution login ("Item"), owner-`select`-only; only edge functions insert/update/delete.
- `plaid_item_secrets` — the per-item `access_token`, same zero-select-policy pattern as `plaid_credential_secrets`.
- `plaid_pending_positions` — staging rows a sync detected but the user hasn't confirmed; nothing here has touched `assets`/`transactions`/`fixed_income_lots` yet.
- `plaid_synced_positions` — idempotency map so a confirmed position's later syncs update it in place instead of re-flagging it for review.

Edge functions (`supabase/functions/plaid-*`), **all deployed `verify_jwt: false`** (see Gotchas — the gateway's own JWT check on CORS preflight breaks browser calls, so every user-invoked one does its own `userClient.auth.getUser()` check instead): `plaid-create-link-token` and `plaid-exchange-token` handle Plaid Link; `plaid-sync` (hourly via `pg_cron`, loops every user's items, the one function here with no browser caller) and `plaid-sync-me` (scoped to the caller, backs the Settings "Sync now" button and the post-connect initial pull) do the actual holdings/balance diffing; `plaid-remove-item` disconnects. All five duplicate the same small credential-lookup + Plaid-fetch snippet rather than sharing a module, and the four user-invoked ones also duplicate a `CORS_HEADERS`/`jsonResponse` pair and an `OPTIONS` short-circuit — see the Gotchas entry below.

Sync is **review-first**: a detected position is written to `plaid_pending_positions`, never directly to the portfolio. `AppLayout.tsx`'s startup effect surfaces a banner the next time the app opens if any are pending; `PlaidReviewModal.tsx` (opened from that banner or from Settings) lets the user fill in anything Plaid didn't supply — RSU/ESPP grant schedules, bond coupon rate/maturity/face value, an empty tax-lot history — before confirming. Confirm calls `executeTool`/`validateWriteToolInput` (exported from `src/lib/claude.ts` for this reuse) with the same tool names the AI command bar's write tools use (`add_stock_transaction`, `add_cash_asset`), so a synced position is written exactly the way a manually-entered one would be.

Confirming also writes a `plaid_synced_positions` row (`recordPlaidSyncLink` in `src/lib/db/plaid.ts`) pointing at whatever `executeTool` just created/touched — this is what `plaid-sync`'s own idempotency check (above) and the Plaid-synced badge (see Data Model → `getPlaidSyncInfo`) key off; without it a confirmed position has nothing stopping it from being re-detected (and re-confirmed, i.e. duplicated) on the next hourly sync. `plaid_synced_positions` has an `insert` policy scoped to the owning user via `plaid_items` (alongside its pre-existing `select` policy) specifically so Confirm — which runs as the signed-in user, not an edge function — can write this itself; it's a plain `INSERT`, never upserted, so the `ON CONFLICT DO UPDATE` / SELECT-privilege issue the secret tables have doesn't apply here.

**Reconciling a matched row against pre-existing manual data**: `matched_asset_id` (set by the natural-key match described above, or picked manually — see below) drives more than just the "Looks like X" label. `add_stock_transaction`/`add_cash_asset` both accept an internal-only `_matchedAssetId` input (never part of either tool's public schema, so the AI command bar's model can never set it) that bypasses their normal ticker+location/insert-new-asset discovery entirely and resolves the asset by id instead — necessary because Plaid's reported location/ownership can differ cosmetically from the existing asset's own fields ("Fidelity" vs "Fidelity Investments") even when the asset itself is correctly identified, which would otherwise silently create a second asset rather than reconcile the first. Both branches re-verify compatibility against the matched asset directly (ticker symbol + asset type for stocks, asset type + `fixed_income_subtype` for cash/fixed-income) before touching anything, so this can never attach data to an incompatible or another user's asset even if `_matchedAssetId` somehow originated from an untrusted path. A matched **flat-balance** row (Cash/401k/HSA/CD — `detected_type === 'cash'`) is safe to auto-reconcile and routes through `update_asset_value` instead (also accepting an internal-only `_assetId`/`_expectedAssetType`, resolving by id rather than the ambiguous `asset_name` — two assets can legitimately share a name). A matched **lot-based** row (Stock, Bond/T-Bill) has no fully-safe automatic merge — the existing manual lot(s) and Plaid's reported lot could be the same purchase or a genuinely different one — so those rows still require an explicit "this isn't a duplicate" checkbox before Confirm is enabled; what changed is that confirming no longer blindly inserts regardless. `_plaidLots` (built by `buildCandidateLotsFromPlaidPayload` in `src/lib/plaidMatching.ts`, from the holding's `_lots` tax-lot breakdown when Plaid reports one, else the single aggregate quantity/cost-basis figure) is diffed against what's already tracked under the matched asset's subtype/lots (`findMatchingLot`, matching purchase date exactly and count/cost within a small rounding tolerance) — a lot already tracked is skipped, not re-inserted, and **nothing is ever deleted**: a lot Plaid doesn't currently report (sparse data, or a brokerage with no per-lot breakdown at all) is left completely untouched rather than treated as evidence something should be removed.

**Manual match when the natural-key match misses**: Plaid has no ownership signal and always guesses `'Individual'` (see Data Model), so an account the user tracks as `'Joint'` (or any other natural-key mismatch) won't auto-match even though the position is the same one — confirming it as "new" would create a duplicate, exactly like it once did in production (a second "Joint Checking" at Chase, `'Individual'`, alongside the real `'Joint'` one). For a row with no automatic `matched_asset_id`, `PlaidReviewModal` offers a dropdown of **structurally compatible** existing assets to link to instead (`compatibleManualMatchCandidates` in `src/lib/plaidMatching.ts`, unit tested) — compatibility is type-exact, never a loose guess: a detected stock lot only lists existing **Stock** assets for the **exact same ticker** (never Crypto, even though both are ticker assets — see `isTickerAsset`); a detected cash balance only lists assets of the **exact same `asset_type`** (`Cash`/`401k`/`HSA` — a 401k can never be linked to a Cash asset); a detected Bond/T-Bill only lists Fixed Income assets with the **exact same `fixed_income_subtype`**. The dropdown is simply absent when nothing compatible exists. Once picked, a manual match is treated identically to an automatic one everywhere else (same reconciliation above, same duplicate-risk checkbox for lot-based types, same sync-link recording) — the only UI difference is the badge reads "Linked to X" instead of "Looks like X".

## Gotchas

**Image attachments require Claude**: Attaching an image in the command bar throws if the active LLM provider is Groq. CSV and PDF work with both providers.

**`is_allowed_email_admin()` bypasses RLS intentionally**: The helper function is SECURITY DEFINER so it can query `allowed_emails` without triggering recursive policy evaluation. Don't remove this without replacing with a safe equivalent.

**RLS on new tables**: Every new Supabase table needs an explicit RLS policy or all writes silently fail with a policy violation. Check `supabase/migrations/` for the pattern used on existing tables.

**A secret table can have RLS enabled with *no* policies at all**: `plaid_credential_secrets` and `plaid_item_secrets` do this deliberately — RLS enabled + zero `select` policy for `authenticated`/`anon` means default-deny, so the row can never be read back by a normal client, only by a service-role edge function. Don't "fix" a Plaid secret query that returns nothing from the browser — that's the point, not a bug. **Never `.upsert()` into a table like this**, though: Postgres requires SELECT privilege to use `INSERT ... ON CONFLICT DO UPDATE` (needed to detect the conflict), so an upsert against a zero-select-policy table gets a real `403 insufficient_privilege` — which, in this app, `src/lib/supabase.ts`'s global `authAwareFetch` then reads as a dead session and force-signs the user out (see the next entry). Use a plain `UPDATE` (with `{ count: 'exact' }` to detect zero-rows-affected) falling back to a plain `INSERT` instead — see `savePlaidCredentials` in `src/lib/db/plaid.ts`.

**A "status" check against a zero-select-policy table needs its own tracking flag, or it lies**: `getPlaidCredentialsStatus()` can't `select` from `plaid_credential_secrets` to check whether a secret exists — so it originally judged "configured" from `plaid_credentials.client_id` alone, which stays true even if the secret write failed (exactly what happened during the 403-upsert bug above: `client_id` saved, the secret never did, and Settings kept claiming "configured" anyway, hiding the real problem). Fixed with a plain `secret_set boolean` on `plaid_credentials`, set by `savePlaidCredentials` only after the secret write actually succeeds. Any future "is X fully set up" check against a write-only table needs the same kind of explicit flag — never infer it from a sibling table you can read.

**Any 403 from `/rest/v1/` force-signs the user out, not just a real auth failure**: `src/lib/supabase.ts`'s `authAwareFetch` wraps every Supabase request and treats **any** 403 from a REST endpoint as proof the session is dead (`shouldForceSignOut`) — it's a blunt heuristic that doesn't distinguish "stale JWT" from "a legitimate RLS/privilege rejection on an otherwise-valid session." Any new table or query that can legitimately return 403 to a signed-in user (not just an expired one) will silently log them out when it does. Design new RLS-restricted writes to avoid ever hitting a 403 under normal use (see the upsert gotcha above) rather than relying on this handler being selective — it isn't.

**Edge functions deployed `verify_jwt: true` can't be called from a browser via `functions.invoke()`**: Supabase's gateway enforces JWT verification on *every* request method when `verify_jwt: true`, including the CORS preflight `OPTIONS` request — but a browser preflight never carries the app's `Authorization` header, so the gateway 401s the preflight before the function code runs, the browser's CORS check fails, and `functions.invoke()` surfaces this as the generic "Failed to send a request to the Edge Function" (indistinguishable from a real network failure — check `function_edge_logs`, not `edge_logs`, for the actual `OPTIONS | 401` to confirm). All five `plaid-*` functions are deployed `verify_jwt: false` for this reason, each doing its own `userClient.auth.getUser()` check instead, and each must handle its own `OPTIONS` request (`CORS_HEADERS` + an early return) and send `Access-Control-Allow-Origin` on every response. Any new user-invoked edge function needs the same treatment.

**Edge functions in this repo don't share code across files**: `setup.sh`/`upgrade.sh` zip each function's `index.ts` in isolation (`cd supabase/functions/<slug> && zip -qr ... index.ts`), so a `_shared/` import would silently break at deploy time. `check-vests`/`check-prices` and all five `plaid-*` functions duplicate small helpers instead — keep duplicated copies in sync by hand when changing them.

**deleteAsset cascade**: There is no `ON DELETE CASCADE` at the DB level. `deleteAsset()` in `src/lib/db/assets.ts` manually deletes `transactions` → `rsu_grants` → `stock_subtypes`, and `fixed_income_lots`, before deleting the asset. Any new child tables added to `stock_subtypes` (or directly to `assets`, like `fixed_income_lots`) must be added to this function.

**Push notifications in production**: Requires `VITE_VAPID_PUBLIC_KEY` in `.env.local` and the three VAPID secrets (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`) set in Supabase dashboard → Settings → Edge Functions → Secrets.

**DB migrations**: Applied via Supabase MCP (`apply_migration` tool) or the Supabase dashboard SQL editor. There is no local Supabase CLI setup — all schema changes go directly to the hosted project. `supabase/sql/self_host_bootstrap.sql` is a standalone idempotent script used by `setup.sh` and `upgrade.sh` to initialize or upgrade a self-hosted Supabase project.

**Migration policy — keep bootstrap.sql in sync**: Every schema change must be reflected in BOTH `supabase/migrations/<timestamp>_<name>.sql` AND `supabase/sql/self_host_bootstrap.sql`. The bootstrap script is the source of truth for self-hosters; `upgrade.sh` re-runs it on every upgrade. Because the bootstrap uses `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, and `DROP COLUMN IF EXISTS` throughout, it is safe to re-run on any existing project at any version. New migrations that add columns should use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in the bootstrap. Migrations that drop columns should use `DROP COLUMN IF EXISTS`. Migrations that rename or change column types need a compatible idempotent form (e.g. a DO block that checks for the old column and backfills before altering).

**`saveSettings` upsert**: Must include `{ onConflict: 'user_id' }` in the upsert call or updates silently fail with a unique constraint error when a row already exists.

**Missing `user_settings` columns**: A 400 from PostgREST on `/rest/v1/user_settings` often means a migration was never applied (column doesn't exist in DB), not a client bug. Check the response body for the actual column name.

**`gh` CLI not available**: `gh` is not installed. Create PRs via the GitHub web URL printed by `git push` instead.

**Notification edge functions**: Each `check-*` function reads `price_alerts_enabled` / `vest_alerts_enabled` / `capital_gains_alerts_enabled` from `user_settings` and skips push (but not DB promotion) when false.

**Adding a new LLM provider**: Add the provider type to `LLMProvider` in `src/store/config.ts`, add a case in `createLLMClient` in `src/lib/llm.ts`, add the model to `MODEL_FOR_PROVIDER`, add a key field to the config store, and add the `llm_provider` value + key column to `user_settings` via a migration and `self_host_bootstrap.sql`.

**OpenAI-format tool definitions**: All tools in `claude.ts` and `autoThemes.ts` use the OpenAI function-calling format (`{ type: 'function', function: { name, description, parameters } }`). `ClaudeAdapter` in `llm.ts` converts these to Anthropic format internally.
